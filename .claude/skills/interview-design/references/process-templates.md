# Interview Process Templates by Role Family

Complete process templates with stage breakdowns, competency mappings, timelines, and interviewer guidance. Each template is a starting point — adapt to your specific role, team, and context.

## 1. Software Engineering (IC Mid-Senior)

**Total interview time:** 3.5-4.5 hours across 4-5 stages
**Target timeline:** 2 weeks (recruiter screen to offer)

### Stage Breakdown

| Stage | Format | Who | What | Duration |
|-------|--------|-----|------|----------|
| 1 | Recruiter Screen | Recruiter | Motivation, logistics, comp alignment, deal-breaker check | 30 min |
| 2 | Technical Screen | Senior Engineer | Coding exercise (medium difficulty) + brief technical discussion | 60 min |
| 3 | System Design or Live Coding | Staff+ Engineer | System design (Senior) or second coding round (Mid) | 60 min |
| 4 | Behavioral Interview | Engineering Manager or trained peer | Collaboration, conflict, ownership, growth mindset | 45 min |
| 5 | HM Final | Hiring Manager | Role fit, team fit, career trajectory, candidate questions | 45 min |

### Competency-to-Stage Matrix

| Competency | Priority | Screen | Tech Screen | Design/Code | Behavioral | HM Final |
|------------|----------|--------|-------------|-------------|------------|----------|
| Coding ability | Must-have | | X | X | | |
| System thinking | Must-have (Senior) | | | X | | X |
| Problem decomposition | Must-have | | X | X | | |
| Collaboration | Must-have | | | | X | X |
| Communication | Must-have | X | X | | X | X |
| Ownership/autonomy | Must-have | | | | X | X |
| Domain expertise | Nice-to-have | | X | X | | |
| Growth mindset | Nice-to-have | | | | X | |

### Key Differentiators
- Mid-level: Stage 3 should be a second coding round (different problem type) rather than system design
- Senior: Stage 3 should be system design — expect candidates to drive the discussion and make trade-off decisions
- For Senior, consider replacing Stage 2 with a take-home if the candidate pool prefers async work

### Common Pitfalls
- Over-indexing on algorithm puzzles that don't reflect actual work
- Not calibrating coding difficulty to level — using the same problem for Mid and Senior
- Skipping the behavioral round because "we just need a strong coder" — collaboration issues are the #1 reason engineers get managed out
- Having the HM do a second technical assessment instead of focusing on role fit and team dynamics

## 2. Software Engineering (Staff/Principal)

| 4 | Technical Deep-Dive | Domain expert (Staff+) | Depth in claimed expertise area, past architecture decisions, technical judgment | 60 min |
| 5 | Cross-functional Behavioral | Product Manager or Eng Manager from adjacent team | Influence without authority, cross-team collaboration, technical leadership | 45 min |

| Communication | Must-have | X | X | X | X | X |

### Key Differentiators
- The HM Screen at this level is substantial — it's a technical and strategic conversation, not just logistics
- System Design scope should be significantly larger than Senior: multi-service, multi-team, platform-level decisions
- The cross-functional behavioral is critical — Staff+ engineers must influence beyond their team
- Coding assessments are typically not included unless the role is unusually hands-on. If included, make it optional or replace one stage.

- Treating this as a "harder version" of the Senior process — Staff+ is a qualitatively different role, not just harder coding
- Not probing organizational impact: "How did you change how engineering worked at your last company?"
- Skipping the cross-functional round — a Staff engineer who can't work with Product is a very expensive problem
- Not having a sufficiently senior interview panel — Staff candidates being interviewed by Senior engineers is awkward and produces poor signal

## 3. Engineering Manager

**Total interview time:** 5-6 hours across 5-6 stages
**Target timeline:** 3 weeks (recruiter screen to offer)

### Stage Breakdown

| Stage | Format | Who | What | Duration |
|-------|--------|-----|------|----------|
| 1 | Recruiter Screen | Recruiter | Motivation, management philosophy preview, logistics, comp | 30 min |
| 2 | HM Screen | Director of Engineering or VP Eng | Leadership philosophy, team management approach, strategic alignment | 60 min |
| 3 | Technical Assessment (lighter) | Staff+ Engineer | Technical credibility check — architecture discussion, not coding. Can they earn engineers' respect? | 45 min |
| 4 | Leadership Scenarios | Eng Manager peer or Director | Behavioral: managing underperformers, handling conflict, building teams, delivering through others | 60 min |
| 5 | Team Simulation / Skip-Level | 2-3 engineers who would report to this person | Candidate meets the team. How do they engage with ICs? Do the engineers want to work for them? | 45 min |
| 6 | Bar Raiser / Skip-Level Up | VP/CTO or cross-functional leader (Product, Design) | Culture, values, cross-functional leadership, long-term organizational fit | 45 min |

### Competency-to-Stage Matrix

| Competency | Priority | HM Screen | Technical | Leadership | Team Sim | Bar Raiser |
|------------|----------|-----------|-----------|------------|----------|------------|
| People management | Must-have | X | | X | X | |
| Technical credibility | Must-have | | X | | X | |
| Delivery/execution | Must-have | X | | X | | |
| Hiring & team building | Must-have | X | | X | | X |
| Strategic thinking | Must-have | X | | | | X |
| Cross-functional collab | Must-have | | | | | X |
| Conflict resolution | Must-have | | | X | | |
| Coaching & development | Must-have | X | | X | X | |
| Communication (up & down) | Must-have | X | | X | X | X |

### Key Differentiators
- The technical assessment is a credibility check, not a coding test — can they have informed opinions on architecture and earn the team's respect?
- The team simulation is uniquely important: if the engineers don't want to work for this person, the hire will fail regardless of other signals
- Leadership scenarios should use real situations: "One of your engineers has missed deadlines 3 sprints in a row. Walk me through your approach."
- The skip-level (meeting with the HM's manager) validates strategic alignment and organizational fit

### Common Pitfalls
- Making the technical bar too high — an EM who can't code doesn't matter if they can make good technical decisions and earn trust
- Making the technical bar too low — an EM who has zero technical intuition will lose their team's confidence
- Not including direct reports in the process — the team's buy-in is essential
- Focusing only on "managing up" scenarios and ignoring "managing down" (coaching, performance management, career development)
- Not probing how they handle underperformers — the #1 failure mode for new EMs

## 4. Product Management (IC)

| 3 | Product Case Study | Senior PM + Engineer | 48-72hr prep case: product strategy, prioritization, or product improvement. 20 min presentation + 40 min Q&A | 60 min |
| 4 | Analytical / Metrics | Data-oriented PM or Data lead | Metrics definition, data-informed decision making, experimentation design | 45 min |

| Communication | Must-have | X | X | | X |
| Data-informed decisions | Nice-to-have | | | X | |
| Technical understanding | Nice-to-have | | | | X |

### Key Differentiators
- The case study is the core of the PM assessment — it simulates the actual job. Give adequate prep time (48-72 hours).
- The analytical round should use real-world scenarios: "How would you measure the success of [feature]? Design an experiment to test [hypothesis]."
- Cross-functional behavioral is essential — PMs who can't collaborate with engineering and design fail regardless of product sense
- For Senior PMs, add a strategy/vision component to the case study

### Common Pitfalls
- Using brain-teaser product questions ("How many golf balls fit in a school bus?") instead of role-relevant cases
- Not including engineers in the process — the PM-Engineering relationship is the most critical success factor
- Evaluating the case presentation on polish rather than thinking quality and adaptability in Q&A
- Not testing analytical skills separately — "product sense" alone misses PMs who can't work with data

- Not asking about work that failed or was killed — reveals resilience and self-awareness

- Making the process too long — top AEs will take competing offers while you deliberate

| 5 | Team / Skip-Level | 3-4 direct reports or senior ICs from the function | How they engage with the team, communication style, earning trust, team's reaction | 60 min |

### Key Differentiators
- Executive hiring is fundamentally different from IC hiring — the stakes are higher, the assessment is broader, and the timeline is longer
- The strategic case should be at the level of a board presentation — this is the candidate's chance to demonstrate executive thinking
- The team/skip-level session is critical — executive hires who don't earn their team's trust fail within 12-18 months
- References are not optional at this level — conduct 4-5 structured reference calls plus back-channel
- Consider a paid advisory engagement (1-2 days) as an alternative to the case study for final candidates

### Common Pitfalls
- Rushing the process under urgency — a bad executive hire costs 6-12 months and millions of dollars
- Not including the team in the process — executives imposed on teams without buy-in face resistance from day one
- Over-indexing on industry experience ("must have done this exact job at a competitor") vs. leadership capability
- Skipping back-channel references — candidate-provided references are selection-biased. For executives, discreet back-channeling is standard practice.
- Not testing how they handle disagreement with the CEO — yes-people at the executive level are dangerous

### Key Differentiators

- For ML roles, probe the full ML lifecycle: data collection, feature engineering, training, evaluation, deployment, monitoring — not just model architecture

### Common Pitfalls
- Using generic software engineering coding problems instead of data-centric problems (SQL, data transformations, feature engineering)

- Not probing data quality — most data engineering work is cleaning, validating, and monitoring data, not building new pipelines
- Assuming ML and Data Engineering are interchangeable — they share some skills but are different roles with different core competencies

### Key Differentiators
- The incident response scenario is the unique differentiator for SRE/DevOps — it tests real-world operational skills that no other format captures
- Probe "toil reduction" mindset: "What's the most impactful thing you automated in the last year? How did you decide it was worth automating?"
- For SRE roles specifically, test SLO/error budget thinking: "How do you balance reliability with feature velocity?"
- On-call philosophy and sustainability should be discussed — burnout is the #1 attrition risk for SRE/DevOps roles

### Common Pitfalls
- Using generic software engineering coding problems — DevOps/SRE coding should focus on scripting, automation, and infrastructure-as-code, not algorithm puzzles
- Not testing incident response — this is a core skill that can't be assessed through conversation alone
- Ignoring the human side: communication during incidents, blameless culture, and collaboration with development teams are as important as technical skills
- Over-indexing on specific tool experience (Kubernetes, Terraform, AWS) vs. underlying systems thinking — tools change, fundamentals don't
- Not discussing on-call expectations honestly — misaligned on-call expectations are the #1 reason SRE/DevOps hires leave within 12 months
